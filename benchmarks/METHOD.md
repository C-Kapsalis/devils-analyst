# How the benchmark is measured

This page says what I measure, how, and where the numbers can mislead you. If
you find a case where the answer key is wrong, or a planted problem that is
not really a problem, please open an issue: that is the most useful feedback
this project can get.

No results are published yet. The README holds `{{DA_*}}` placeholders that
`report.py` fills from the first full run.

## The question

Does a small model handle marketing data better with Devil's Analyst loaded
than without it? "Better" means what a careful senior analyst does before
anyone moves budget:

1. finds the problems in the data that change the answer,
2. reaches the right decision on the proposal in front of it,
3. ranks the problems that should stop a decision first,
4. leaves correct details alone,
5. calls clean work clean.

## Setup

- **Model under test:** Claude Haiku 5.5, in Claude Code, through `claude
  plugin eval`. I chose the small model on purpose: a checklist should help
  most where the model has the least slack.
- **Two arms:** the same prompt and the same files, once with the plugin
  loaded and once without it (`claude plugin eval` ablation, `with-without`).
- **Prompt:** each case is a request a marketer would send ("Which version
  should we go with?", "Is there anything I'm missing?"), with exports in
  `resources/`. The model writes `report.md`; the graders read that file.
  Tools: Read, Glob, Grep, Skill, Write; at most 40 turns.
- **Runs:** 3 per case per arm.
- **Judge:** the `claude plugin eval` default, three votes per LLM grader;
  a grader passes on a majority.

## The cases

Run `python3 scripts/count.py` for the current counts. On 2026-10-17:

| Group | Cases | What a case is |
|---|--:|---|
| Focused | 62 | A clean export built around a named trap: averaged rates, summed daily users, a sample ratio mismatch, stacked platform revenue, Simpson's paradox, a promotion's pull-forward, regression to the mean. Graded on the right number and the right recommendation. |
| Breadth | 36 | A realistic draft report, memo or proposal with the exports behind it. Each hides four to six subtle problems and usually two decoys, and asks for a decision. |
| Audits and reviews | 12 | An account, setup or report export to audit or review (Google Ads, Performance Max and Meta, GA4 and UTMs, email and CRM, a Power BI model, six reports), with planted problems, decoys, and one clean control. |

Each case except five is generated by a script in
[builder/cases/](builder/cases/). The script simulates the exports with a
fixed seed, computes the true answer in code, asserts that the naive answer
differs from it, and writes the case. The graders quote the computed numbers,
so the answer key and the data cannot drift apart. The five hand-written
cases (`cac-two-facts`, `email-mix`, `ga4-users`, `gsc-position`,
`roas-stacking`) were the first ones I wrote; the builder never touches them.
The `designs-*.md` files in [builder/](builder/) are the design notes behind
seven families of cases.

Rebuild everything:

```bash
python3 benchmarks/builder/build_all.py
```

The output is byte-identical to `benchmarks/cases/`; `git status` after a
rebuild should show no change.

## Graders

Every case has its own LLM graders, each with the ground truth written into
it, plus a `skill-fired` check. The ones shared across groups:

| Grader | Weight | Passes when |
|---|--:|---|
| `subtle-recall` (breadth) | 3 | At least 3 of the 4 or 5 planted problems (4 of 6 in one case) are named with evidence: a number, a date, a row. |
| `decision` | 3 (one case 2) | The report reaches the right call on the proposal, for the right reason. |
| `no-false-alarms` (breadth) | 2 | No decoy is presented as a problem. |
| `planted-recall` (audits, reviews) | 3 | Enough planted problems found, with evidence. |
| `must-fix-first` (audits, reviews) | 2 | The problems marked Must fix are ranked first. |
| `decoys-left-alone` (audits, reviews) | 2 | No decoy is presented as a problem. |
| `called-clean` (control) | 3 | The clean report is called sound. |
| Case-specific (focused) | 1 to 3 | The computed number or recommendation that case is about (`srm-detected`, `users-not-summed`, `weighted-position` ...). |
| `skill-fired` | not scored | With-plugin arm only: a `devils-analyst:` skill was called. |

A run's score is the weighted share of its graders that passed.
[report.py](report.py) reports, per group and overall, the mean score, the
share of runs where every grader passed, and each shared grader's pass rate,
with the counts next to every percentage.

There is no `check_facts.py` here, unlike in Second Read: these cases do not
ask for a rewrite, so there is no rewritten text to scan for invented facts.
The numbers a report must get right are in the graders.

## Reproduce it

You need Claude Code with `claude plugin eval`, and Python 3.9 or later for
the scripts (stdlib only). From the repo root:

```bash
# 1. Optional: rebuild the cases.
python3 benchmarks/builder/build_all.py

# 2. Run both arms and keep the log.
claude plugin eval . --eval-dir benchmarks/cases --scaffold --allow-tools Write Bash --model haiku -j 6 --runs 3 --trust-plugin --no-publish | tee benchmarks/eval.log

# 3. Write benchmarks/results/<date>.md, the chart in assets/, and the
#    numbers in README.md.
python3 benchmarks/report.py benchmarks/eval.log
```

`--scaffold` runs each case's `scaffold.sh`, which only writes the fixture
files into the run's workspace; read one before you run it. The log prints
the API cost of every run and the total at the end. To run one group, pass
the cases you want with your shell (for example a copy of
`benchmarks/cases/bx-*`).

## Limits

I would rather you know these before you quote a number.

- **Synthetic data.** Every export was simulated for the benchmark, with the
  problems planted on purpose. Real exports are messier, and the hardest
  real problems (is the goal right? is the margin right?) cannot be planted.
- **Clean exports flatter the model.** In early runs, Claude Haiku 5.5
  without the plugin already avoided most single-number traps when the
  export was clean and the question pointed at the trap. The breadth group
  exists because that is not how data arrives: the trap sits next to four
  others and two decoys, inside a draft someone else wrote.
- **Three runs per arm.** One run moves a case's pass rate by 33 points.
  Read differences of a few points as noise.
- **An LLM judge.** The graders carry the computed answer, which helps, but
  a judge can still pass a vague report or fail a correct one phrased
  differently. I have not yet measured agreement with a human grader.
- **One model, one host.** The numbers are for Claude Haiku 5.5 in Claude
  Code. The adapters for other agents load the same method but are not
  benchmarked.
- **The same person wrote the cases and the skills.** A benchmark written by
  the person who wrote the prompt can flatter it, even when the answer key is
  computed. Cases from other people are the best fix; see
  [CONTRIBUTING.md](../CONTRIBUTING.md).
